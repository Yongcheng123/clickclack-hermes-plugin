Hermes × ClickClack Workshop

从连接 Bot，到多人协作完成一个项目

阶段一把每个人自己的 Hermes 接入同一个 ClickClack Channel；阶段二让各自的 Bot 自动认领 Mobius Issue、完成独立模块、提交 PR，并由主持人的 Review Agent 集成。

总时长：约 60 分钟 7–8 位参与者 公开 Repo + 假数据 最后更新：2026-07-29

阶段一：把自己的 Hermes 连接到 ClickClack

参与者只需要复制真正的 Prompt。Bot 表单是网页填写参考，不会提供复制按钮。

01让 Hermes 安装 Plugin，并及时允许 Access
02安装期间，在 ClickClack 创建个人 Bot
03把 Token 交给 Hermes，一次配置并启用
04在 Channel 里完成 PONG 测试
开始前需要：自己的 Hermes Studio Web UI、可登录的 GitHub 账号，以及访问 Hermes Workshop ClickClack 的权限。
关于 Hermes 版本：参与者不需要记版本号，也不需要自己运行 版本检查。能正常对话是第一步；安装还需要当前 Hermes 支持 plugins 和 gateway。下面的 Prompt 会自动检查， 如果缺少这些能力，直接联系主持人换用备用 Studio。
Access 很重要：Hermes 安装时可能请求 Terminal、文件、Git 或网络 Access。看到请求后要立即允许当前会话，否则 Hermes 会停下来等待。 只授权当前 Hermes 完成本次操作。
备用 Hermes Studio：优先使用自己的 Hermes。自己的 Studio 无法登录、无法启动或无法安装 Plugin 时，再联系主持人分配一个备用实例。 同一时间一个实例只给一位参与者使用。

步骤 1：让 Hermes 安装 Plugin

  1. 登录自己的 Hermes Studio，开启一个新会话。
  2. 复制下面 Prompt 发给 Hermes。
  3. 看到 Access 请求立即允许；Hermes 工作时同步进行步骤 2。
Prompt 1 · 安装并检查 Plugin 
请在当前 Hermes Studio 安装这个 Platform Plugin：
https://github.com/Yongcheng123/clickclack-hermes-plugin

要求：
1. 只操作当前 Studio；确认当前 Profile、实际 HERMES_HOME，以及存在
   plugins 和 gateway 命令。不要因为具体版本号暂停安装。
2. 如果需要 Terminal、文件、Git 或网络 Access，立即向我请求；获批后继续。
3. 如果 hermes 不在 PATH，使用 /opt/hermes/.venv/bin/hermes。
4. 未安装时运行：
   hermes plugins install Yongcheng123/clickclack-hermes-plugin --no-enable
   已安装时运行：
   hermes plugins update clickclack-hermes
5. 暂时不要启用，也不要索取 Token；停在 not enabled，等待我下一条消息。
6. 安装器创建 Plugin 目录的模板 .env 是正常的，但不要把真实 Token 写进去。
7. 不要覆盖现有模型、MCP、Gateway、Memory 或其他配置。

完成后只报告：HERMES_HOME、安装路径、Plugin 状态，以及 plugins/gateway
命令是否可用。
预期结果：Plugin 能被 hermes plugins list 发现； not enabled 表示安装成功、正在等待 Bot Token，不是报错。

步骤 2：在 ClickClack 创建自己的 Bot

进入 Workspace settings → Automation → Bots & agents， 点击 Add bot。这部分是网页表单，不是 Prompt，请逐项填写。

打开 Bots & agents

字段怎么填说明
Display name你的名字 Hermes示例：Ken Hermes
Handle你的名字-hermes唯一、小写英文和连字符
OwnershipUser-owned bot每位参与者都选这个
ConnectionManual token不要选 OpenClaw Setup code
ScopeRead & write不要选 Admin
Token namehermes-workshop方便活动后撤销
Token 只显示一次：创建后立即复制以 ccb_ 开头的 Token。不要把真实 Token 发到 ClickClack、Git、文档或公开群聊。

步骤 3：让 Hermes 完成配置和启用

回到刚才同一个 Hermes 会话。确认它已报告 clickclack-hermes not enabled，复制下面 Prompt，并且只替换 Token 占位符。

Prompt 2 · 完成配置、启用和检查 
请继续配置并启用刚安装的 clickclack-hermes。

只操作当前 Studio。下面是我授权用于本次 Workshop 的 Bot Token；收到后直接
继续，不要要求轮换，也不要在回复或工具输出中显示它。

CLICKCLACK_BOT_TOKEN: <PASTE_YOUR_CCB_BOT_TOKEN_HERE>

请执行：

4. 运行 Plugin 自带 doctor。
5. 重启当前 Hermes Gateway，不要重启其他服务器或容器。
6. 最后只报告：
   - Plugin 是否 enabled
   - Doctor 是否全部 PASS
   - Gateway 是否显示 ClickClack connected
   - 下一步应使用的 Bot handle

如果需要新的 Access，请向我请求，获批后继续。

步骤 4：在 ClickClack 做 PONG 测试

回到 #general，手动发送： @<YOUR_BOT_HANDLE> 请只回复 PONG。 因为启用了 require_mention，必须准确 @ 自己的 Bot。

成功标准：Bot 在对应消息或 Thread 中回复 PONG； 不 @ Bot 的普通消息不会触发。

03开发、测试、同步 Mobius、提交 PR
04Review Agent 验收并合入 integration
开始前：阶段一 PONG 已通过；Hermes 已获得 Mobius 和 GitHub 访问权限。遇到 Access 请求要及时允许，否则 Bot 会停下来等待。

参与者 Prompt · 自动认领、开发、同步和提交 
You are my implementation agent for the Hourly Dashboard workshop.

My Mobius user name: <YOUR_MOBIUS_USER_NAME>
Mobius team: 周四练习 (THU)
Parent issue: THU-1
Repository: https://github.com/Yongcheng123/hourly-dashboard-practice
Participant PR base: integration/workshop

Execute the complete workflow for me:

1. Confirm that you can read and update Mobius and can use GitHub. If access is
   missing, ask me for that access and continue after approval. Do not stop silently.

2. Read THU-1 and all of its direct child issues. Eligible issues must:
   - have no assignee;
   - be in Todo or Backlog;
   - not already contain a TAKEN comment from another participant.

3. Refresh the children immediately before claiming. Randomly choose one eligible
   issue. Assign it to the exact Mobius user name I provided, change it to
   In Progress, and add:
   TAKEN
   Owner: <YOUR_MOBIUS_USER_NAME>
   Hermes bot: current bot
   Started: current time

4. Re-read the issue and verify that the assignee is me and the state is
   In Progress. If another participant claimed it first, do not overwrite them;
   choose another eligible issue and repeat. If no eligible issue remains, tell
   me and stop without changing code.

5. Read the claimed issue's full description and acceptance criteria. Add a PLAN
   comment to that issue with the allowed files, approach, and risks. Do this
   yourself; do not ask me to copy a PLAN template.

6. Fork or clone the public repository. Create
   feat/<CLAIMED_ISSUE_ID>-<SHORT_NAME>
   from upstream/integration/workshop.

7. Edit only the files allowed by the issue. Do not modify DashboardShell,
   globals.css, shared data/types, package.json, or the lockfile unless the issue
   explicitly allows it. Do not use production credentials or real campaign data.

8. Implement the acceptance criteria using the existing fake data and visual
   language. Keep the dashboard responsive and accessible.

9. If blocked, add a BLOCKED comment to the claimed Mobius issue explaining the
   blocker and what access or decision is needed, then ask me. Do not ask me to
   write the Mobius comment manually.

10. Run npm run lint and npm test. Fix failures within the allowed scope.

11. Commit and push the feature branch. Open a pull request to:
    Yongcheng123/hourly-dashboard-practice:integration/workshop
    The PR title must include the claimed Mobius issue ID.

12. Add a READY comment to the claimed Mobius issue with branch, PR URL, changed
    files, lint result, test result, and risks. Move the issue to In Review.
    Do this yourself; do not ask me to copy a READY template.

13. Report only: claimed Issue ID/title, branch, PR URL, test results, and any
    item that needs human review. Never merge the PR yourself.
参与者完成标准：Bot 已自动认领一个 Issue；Mobius 显示 In Review 和 READY 评论；GitHub PR 的 Base 是 integration/workshop。

主持人：让 Review Agent 集成

等参与者 PR 到齐后，给主持人的 Agent GitHub 和 Mobius 权限，再发送下面 Prompt。Review Agent 会更新 Mobius、逐个合并到 integration，并创建最终 PR。

主持人 Review Agent Prompt 
You are the integration and review agent for the Hourly Dashboard workshop.

Repository: https://github.com/Yongcheng123/hourly-dashboard-practice
Mobius team: 周四练习 (THU)
Parent issue: THU-1
Participant PR base: integration/workshop
Final branch: main

1. Read THU-1 and every child issue, including assignee, state, comments, and
   acceptance criteria.
2. Find every PR targeting integration/workshop and match it to one THU child.
3. For each PR verify allowed files, acceptance criteria, secrets, responsive
   layout, accessibility, npm run lint, and npm test.
4. If incomplete or conflicting, leave concrete PR feedback, add a BLOCKED review
   comment to Mobius, and keep the issue In Review. Do not silently rewrite a
   participant's feature.
5. Merge acceptable PRs into integration/workshop one at a time.
6. After every merge rerun npm run lint and npm test.
7. Update the matching Mobius issue to Done and comment the merge commit.
8. After accepted work is integrated, open one final PR from
   integration/workshop to main. Summarize accepted features, skipped work,
   test results, and remaining risks in THU-1.
9. Do not merge the final PR to main. The human host decides.

If GitHub or Mobius access is missing, ask the host and stop. Never expose secrets.

  • 55–60 分钟：展示组合效果、最终 PR 和 Mobius 回顾。
