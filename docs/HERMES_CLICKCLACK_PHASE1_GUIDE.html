Hermes × ClickClack Workshop

从连接 Bot，到多人协作完成一个项目

阶段一把每个人自己的 Hermes 接入同一个 ClickClack Channel；阶段二让各自的 Bot 自动认领 Mobius Issue、完成独立模块、提交 PR，并由主持人的 Review Agent 集成。

总时长：约 60 分钟 7–8 位参与者 公开 Repo + 三源固定快照 最后更新：2026-07-30

阶段一：把自己的 Hermes 连接到 ClickClack

参与者只需要复制真正的 Prompt。Bot 表单是网页填写参考，不会提供复制按钮。

01按 Mobius 状态选择 Prompt 1
02安装 Plugin，并按需配置 Mobius MCP
03创建 Bot，完成 ClickClack 配置
04统一重载后验证 Mobius 和 PONG
开始前需要：自己的 Hermes Studio Web UI、可登录的 GitHub 账号、自己的准确 Mobius 显示名，以及访问 Mobius 和 Hermes Workshop ClickClack 的权限。
关于 Hermes 版本：参与者不需要记版本号，也不需要自己运行 版本检查。能正常对话是第一步；安装还需要当前 Hermes 支持 plugins 和 gateway。下面的 Prompt 会自动检查， 如果缺少这些能力，直接联系主持人换用备用 Studio。
Access 很重要：Hermes 安装时可能请求 Terminal、文件、Git 或网络 Access。出现 AGENT NEEDS CLARIFICATION 时，选择第一个 “全部授予：Terminal + 文件读写 + Git + 网络”。 安装 Plugin 需要执行命令、写入 Plugin 目录、从 GitHub 下载代码并访问网络； 不要选择“只读”，也不要点 Dismiss，否则安装会暂停或失败。 权限只授权给当前 Hermes Studio 完成本次 Workshop。
备用 Hermes Studio：优先使用自己的 Hermes。自己的 Studio 无法登录、无法启动或无法安装 Plugin 时，再联系主持人分配一个备用实例。 同一时间一个实例只给一位参与者使用。

备用 Studio 1 备用 Studio 2 备用 Studio 3 备用 Studio 4

本阶段只重启一次：不要让 AI 先检测 Mobius。参与者根据 自己是否已经配置 Mobius MCP，直接选择对应的 Prompt 1；补齐 MCP、安装 Plugin 并完成 Bot 配置后，才统一重载并验证。不要为 MCP 和 Plugin 分别重启。

步骤 1：选择 Prompt 1，并安装 Plugin

  1. 登录 Mobius，在左下角账户区域确认自己的准确显示名。
  2. 登录自己的 Hermes Studio，开启一个新会话。
  3. 不要让 AI 检测 Mobius。你知道已经连接时选择版本 A；没有连接或不确定时选择版本 B。
  4. 把选择的 Prompt 1 发给 Hermes；看到 Access 请求，选择第一个 “全部授予：Terminal + 文件读写 + Git + 网络”。
  5. Hermes 执行期间，同步在 ClickClack 创建自己的 Bot。

阶段二：Bot 自动认领 Issue 并完成 PR

参与者不需要手动挑选 Issue、手动分配、手动写 PLAN/BLOCKED/READY。 使用阶段一确认并连接 MCP 时填写的同一个 Mobius 用户名，把一个 Prompt 发给自己的 Hermes。当前基线已经包含三张 Chime 数据源、345 条小时记录 和完整 18 项指标；参与者只完成各自隔离的 Feature。

01Bot 在 THU-1 下随机选择未分配 Issue
02自动分配、In Progress、评论 TAKEN
03开发、测试、同步 Mobius、提交 PR
04Review Agent 验收并合入 integration
开始前：阶段一 PONG 已通过；Hermes 已获得 Mobius 和 GitHub 访问权限。遇到 Access 请求要及时允许，否则 Bot 会停下来等待。
当前项目基线：Repo 已内置 2026-07-24 至 2026-07-28 的 三张 Chime FeedTV 固定快照，共 345 条小时记录、18 项指标。Agent_B 在 7 月 24 日只有 9/24 小时，这是原始快照中的真实缺口。Workshop 不连接 实时 API，也不需要 Beeswax MCP 或生产凭据。

   - 没有 Assignee；

3. 在认领前立即刷新一次子 Issue 列表，从符合条件的 Issue 中随机选择一个。

   没有可认领的 Issue，告诉我并停止，不要修改代码。

5. 阅读已认领 Issue 的完整描述和 Acceptance Criteria。由你直接在该 Issue

   或填写 PLAN 模板。

   feat/<CLAIMED_ISSUE_ID>-<SHORT_NAME>

   DashboardShell、RawHourlyTable、SourceComparisonTable、globals.css、
   chime 数据文件、共享 data/types、package.json 或 lockfile。
   不要使用生产环境凭证，也不要添加仓库快照之外的真实 Campaign 数据。

8. 使用仓库现有的三张 Chime 固定快照和视觉风格完成 Acceptance Criteria。
   不连接实时 API，不伪造 Agent_B 缺失小时，并保持 Dashboard 响应式和可访问。

9. 如果遇到阻塞，由你直接在已认领的 Mobius Issue 添加 BLOCKED 评论，说明
   阻塞原因以及需要的 Access 或决策，然后再向我提问；不要让我手动写评论。

10. 运行 npm run lint 和 npm test，并在允许修改的范围内修复失败项。

11. Commit 并 Push Feature Branch，然后向以下 Base 创建 Pull Request：
    Yongcheng123/hourly-dashboard-practice:integration/workshop
    PR 标题必须包含已认领的 Mobius Issue ID。

12. 由你直接在已认领的 Mobius Issue 添加 READY 评论，包含 Branch、PR URL、
    修改文件、Lint 结果、Test 结果和风险，并把 Issue 改为 In Review；
    不要让我手动复制或填写 READY 模板。

13. 最后只向我报告：认领的 Issue ID/标题、Branch、PR URL、测试结果，以及
    需要人工检查的事项。绝对不要自行合并 PR。
参与者完成标准：Bot 已自动认领一个 Issue；Mobius 显示 In Review 和 READY 评论；GitHub PR 的 Base 是 integration/workshop。
